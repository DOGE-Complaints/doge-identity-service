## Зачем простыми словами
Сервис доверяет токену от Supabase, проверяя ряд полей (кто выдал — `iss`, кому — `sub`, не истёк ли — `exp`, и роль `authenticated`). Но **одно поле спека требует проверять, а код не проверяет** — `aud` («для кого предназначен токен», должен быть `authenticated`). Без этой проверки токен, выпущенный для другой аудитории, теоретически прошёл бы. Плюс есть мелкий технический вопрос: ключ для проверки подписи импортируется из «сырой» строки секрета, а спека изначально предполагала иную (base64url-обёрнутую) форму. Тесты зелёные — значит на практике, видимо, секрет действительно сырой, но это надо **подтвердить на живом токене Supabase**, а не на догадке. Цель стори (уровень требований): решить, вводим ли проверку `aud`, и зафиксировать корректную форму импорта ключа.

## Scope (только требования)
- **Решение по `aud`:** определить, **обязателен ли** `aud=authenticated` к валидации. Целевое требование спеки — да ([`09:43`](../../../requirements/09-supabase-jwt-validation.md)). Требование стори: либо зафиксировать «валидируем `aud=authenticated`» (и тогда это становится критерием приёмки), либо осознанно пометить в спеке 09 как намеренно-не-валидируемое с обоснованием. Решение должно опираться на фактическое содержимое реального Supabase-токена.
- **Сверка формы импорта ключа:** подтвердить на **реальном** Supabase-токене, какая форма ключа верна — сырая строка `OctKey.import_key(jwt_secret)` (как в коде) или base64url-обёрнутая `{"kty":"oct","k":b64url(secret)}` (как изначально в спеке). Зафиксировать единственно-верную форму в коде/спеке так, чтобы они совпадали. Это **сверка-санити**, а не переписывание валидатора вслепую.
- **Согласование спеки и кода:** после решения по `aud` и по импорту — устранить расхождение между [`09`](../../../requirements/09-supabase-jwt-validation.md) и [`supabase_validator.py`](../../../../src/core/auth/supabase_validator.py) (любой из двух источников приводится в соответствие, без «честных note» о расхождении).

## Вне scope
- Переход на RS256/JWKS, ротация ключей, асимметричная проверка — отдельные темы (OIDC-примитивы существуют, но не подключены — deferred eID).
- Изменение остальных уже-корректных проверок (`iss`/`sub`/`exp`/`role`) — они подтверждены аудитом как верные (§5).
- Любая реализация enforcement (как именно зарегистрировать claim в registry) — этап реализации; здесь фиксируется только **что** должно валидироваться.

## Точки в коде (текущее состояние)
- **`aud` не зарегистрирован → не валидируется:** [`supabase_validator.py:18-22`](../../../../src/core/auth/supabase_validator.py) — `JWTClaimsRegistry` объявляет essential только `iss`/`sub`/`exp`; `aud` отсутствует. Роль проверяется отдельной строкой [`supabase_validator.py:34-35`](../../../../src/core/auth/supabase_validator.py) (`role != "authenticated"`), но это **не** `aud`.
- **Импорт ключа из сырой строки:** [`supabase_validator.py:17`](../../../../src/core/auth/supabase_validator.py) — `self._key = OctKey.import_key(jwt_secret)` (сырой секрет, без base64url-обёртки).
- **Спека требует `aud`:** [`09:43`](../../../requirements/09-supabase-jwt-validation.md) (`aud=authenticated`), а note [`09:48`](../../../requirements/09-supabase-jwt-validation.md) честно признаёт, что фактически не валидируется (G-5). Форма импорта обсуждается в [`09:93-94,126`](../../../requirements/09-supabase-jwt-validation.md).

## Acceptance Criteria
- [ ] Принято и задокументировано решение по `aud`: либо `aud=authenticated` валидируется (зафиксировано как требование к валидатору), либо в спеке [`09`](../../../requirements/09-supabase-jwt-validation.md) явно зафиксировано «намеренно не валидируется» с обоснованием.
- [ ] Если решение — валидировать: критерий проверяем тестом (токен с `aud≠authenticated` отклоняется; токен с `aud=authenticated` проходит).
- [ ] Форма импорта ключа подтверждена против **реального** Supabase-токена (сырая строка vs base64url-обёртка); код и спека [`09`](../../../requirements/09-supabase-jwt-validation.md) приведены к одной форме.
- [ ] Расхождение G-5 между [`supabase_validator.py`](../../../../src/core/auth/supabase_validator.py) и спекой 09 устранено (нет открытых «честных note» о несоответствии).
- [ ] Регрессий нет: ранее-корректные проверки `iss`/`sub`/`exp`/`role` сохранены (базовая линия — зелёная сюита из аудита §6).
