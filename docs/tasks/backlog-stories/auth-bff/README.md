# 📌 Записка: зачем этот пакет (auth-bff) — простыми словами

> **Статус пакета:** 🟦 **POST-MVP** (решено 2026-06-28 — не берём сейчас, делаем после MVP).
> **Для кого записка:** для будущей меня, которая забудет контекст. Прочитай это — и поймёшь, зачем пакет и как к нему вернуться без стресса. Технический контракт (детали для сборки) — отдельно: [`auth-bff-proxy-design-2026-06-27.md`](../../../analysis/auth-bff-proxy-design-2026-06-27.md).

## 1. С чего всё началось (чтобы вспомнить)

У Supabase два ключа:
- **anon-ключ** — «обычный пропуск», *публичный*, его не страшно держать в браузере.
- **service_role-ключ** — «мастер-ключ от всего», обходит все правила доступа. В браузере его быть **не должно никогда**.

В `spa-app/.env` случайно лежал **мастер-ключ**, а браузерные настройки уезжают в код всем пользователям → потенциальная утечка. Это закрыла отдельная стори (убрали ключ с фронта).

**Важно (чтобы не путаться потом):** фронт этот мастер-ключ **не использовал** — логин работает на обычном ключе. То есть мастер-ключ был просто мусором в настройках, и «без него сайнап не работал» — это совпадение (заработало от адреса + обычного ключа, которые приехали в той же пачке). **Этот пакет — НЕ про мастер-ключ.**

## 2. Что этот пакет на самом деле делает

Сейчас браузер **сам** ходит в Supabase логиниться (с обычным ключом). Мы решили, чтобы браузер ходил **только к нашему identity**, а identity сам общался с Supabase. То есть identity становится **посредником-вахтёром** между браузером и Supabase.

**Аналогия:** раньше гость сам бегал в банк с картой в кармане. Теперь у входа стоит наш консьерж (identity): гость отдаёт ему поручение, консьерж сам ходит в банк, а гостю выдаёт только пронумерованный жетон («печеньку»). Карта и наличные (ключи и токены Supabase) к гостю больше не попадают.

**Зачем:** в браузере вообще не остаётся ничего от Supabase — взломают страницу, красть нечего. Плюс всё через один наш адрес.

## 3. Что для этого надо построить (и почему это не «пара строк»)

identity сейчас умеет только **проверять** уже выданный токен. Логина у него нет вообще. Значит надо добавить **с нуля**:
- «дверь» для логина/регистрации/сброса пароля (эндпоинты),
- общение с движком авторизации Supabase (GoTrue) на сервере,
- механизм «печеньки» (httpOnly-cookie) с автообновлением токенов на сервере,
- защиту от подделки запросов (CSRF).

Это разложено на 3 задачи: [AUTHBFF-01](STORY-IDS-AUTHBFF-01-gotrue-proxy-endpoints.md) (двери + клиент), [AUTHBFF-02](STORY-IDS-AUTHBFF-02-cookie-session-refresh-csrf.md) (печенька — ядро), [AUTHBFF-03](STORY-IDS-AUTHBFF-03-magic-link-reset-email-redirect.md) (письма: magic-link/сброс/подтверждение email).

## 4. Почему POST-MVP (а не сейчас)

Текущая схема (браузер ↔ Supabase напрямую с обычным ключом) — **стандартная и безопасная**: обычный ключ публичный, защищён правилами доступа. Дыры в ней **нет** (дыра была только в мастер-ключе, и она уже закрыта). Поэтому это **улучшение, а не пожар**. Берём после MVP, когда дойдут руки и появится смысл (единый домен, ноль Supabase в браузере).

**Триггер «пора брать»:** когда захотим, чтобы в браузере не было вообще никаких Supabase-кредов, или появятся требования аудита/комплаенса на единый контур логина.

## 5. Честный размен (чтобы потом не сомневаться в решении)

- **Плюс:** браузер чистый (ни ключей, ни токенов); один наш домен; украсть из браузера нечего; единая точка лимитов/аудита логина.
- **Минус:** identity заметно усложняется (печеньки, обновление токенов, CSRF, обработка писем) и каждый логин делает лишний «прыжок» (чуть медленнее).

Раньше так делать было **не обязательно**. Мы выбрали это осознанно ради «ноль Supabase в браузере». Если в будущем покажется «зачем мы это усложнили» — ответ здесь: ради чистого браузера, по нашему решению, а не потому что было сломано.

## 7. 🤖 Промпт для отдельного SPA-диалога (фронтовая часть)

> Когда дойдём до реализации — открой фокусную сессию в репозитории **spa-app** и вставь промпт ниже. Он просит ассистента построить фронтовую половину перехода (браузер перестаёт ходить в Supabase напрямую, ходит в identity).

```
Контекст: мы переводим авторизацию на модель identity-BFF — браузер больше НЕ ходит в Supabase
напрямую, а логинится через наш identity-сервис, который проксирует Supabase и держит сессию в
httpOnly-cookie. Бэкенд identity (эндпоинты) строится отдельно в пакете doge-identity-service
auth-bff (AUTHBFF-01/02/03). Твоя задача — ТОЛЬКО фронтовая половина в spa-app.

Сначала прочитай (это SSOT, не выдумывай сверх них):
- doge-identity-service/docs/analysis/auth-bff-proxy-design-2026-06-27.md (контракт эндпоинтов + модель cookie)
- spa-app/docs/analysis/identity-supabase-frontend-split-2026-06-16.md (§8, §10, §14 — что было на фронте)
- spa-app/docs/tasks/backlog-stories/security-hardening/STORY-SPA-SEC-02-supabase-credential-boundary.md

Затем по .cursor/rules/analysis.mdc (только проверяемые claims с file:line; ничего не ломать молча):
1. Найди в коде ВСЕ места прямого использования @supabase/supabase-js Auth:
   src/auth/supabaseClient.js, src/pages/LoginPage.jsx (signUp/signInWithPassword/signInWithOtp/
   resetPasswordForEmail), src/auth/useAuthSession.js (getSession/onAuthStateChange),
   src/auth/identityService.js. Составь карту «вызов Supabase → новый identity-эндпоинт» по контракту.
2. Спланируй замену (НЕ реализуй сразу — сначала зеркало + план):
   - login/signup/logout/magic-link/reset → fetch к identity ('POST /auth/...') с credentials:'include';
   - сессия — через httpOnly-cookie (identity ставит), браузер токены НЕ хранит;
   - useAuthSession → опрос GET /auth/session вместо Supabase-listener;
   - убрать @supabase/supabase-js из браузерного Auth-потока (или оставить только типы);
   - убрать ВСЕ VITE_SUPABASE_* из браузерного .env / .env.example.
3. Учти: CORS с credentials (credentials:'include' + точечный origin), CSRF-заголовок на мутациях,
   обработка ответа 403 verification_required (плоский {error,reason,verify_url}) — это НЕ конверт.
4. Зафиксируй зависимость: фронт не зарелизить, пока в identity не готовы AUTHBFF-01/02/03;
   до тех пор — за фиче-флагом.
Выдай: зеркало текущего состояния, план замены по файлам, список новых тестов. Реализацию — после ревью плана.
```

> Промпт намеренно просит «сначала зеркало и план» — чтобы не переписать фронт вслепую до готовности бэкенда.
