# Telnyx integration spec для DOGEstonia phone-verification

Дата: 2026-06-10  
Статус: integration spec / SPIKE-ready  
Источник истины со стороны DOGEstonia: `telnyx-integration-architecture-brief-2026-06-10.md`  
Область: реализация адаптера `TelnyxSmsSender` для тонкого порта `SmsSenderPort.send(to_e164, text)`.

---

## 1. Вердикт по форку: Messaging API vs Verify API

### Решение

**Выбираем Путь A — Telnyx Messaging API.**

Причина: архитектурный контракт DOGEstonia требует тонкого сменного SMS-провайдера: ядро DOGEstonia генерирует OTP, хранит hash/TTL/attempts и сверяет код, а провайдер только доставляет готовый SMS-текст. Telnyx Messaging API поддерживает прямую отправку сообщения через `POST /v2/messages` с нашим `text`, `to` и `from`, что совпадает с портом `SmsSenderPort.send(to_e164, text)`.

Telnyx также имеет Verify API, но это managed OTP-провайдер: Telnyx генерирует/доставляет/проверяет verification token. Это полезно как будущий альтернативный адаптер, но не должно быть базовым путём для текущего провайдер-agnostic контракта.

### Факты из документации Telnyx

1. Telnyx Messaging API позволяет отправить сообщение через `POST https://api.telnyx.com/v2/messages` с полями `from`, `to`, `text`.
   Source: https://developers.telnyx.com/docs/messaging/messages/send-message

2. API reference для `POST /messages` описывает endpoint как отправку message with Phone Number, Alphanumeric Sender ID, Short Code or Number Pool. Текущие messaging resources: `long-code`, `short-code`, `number-pool`, `alphanumeric-sender-id`.
   Source: https://developers.telnyx.com/api-reference/messages/send-a-message

3. Telnyx 2FA guide прямо говорит: Verify API стоит рассмотреть первым, но DIY guide через Messaging API предназначен для случаев, когда нужен full control over the 2FA flow. Для DOGEstonia это как раз требование: OTP остаётся в нашем ядре.
   Source: https://developers.telnyx.com/docs/messaging/messages/2fa

4. Telnyx Verify API существует и предназначен для carrier-grade 2FA через SMS/voice/WhatsApp OTP.
   Source: https://developers.telnyx.com/docs/identity/verify

### Рекомендация

Для PV-06/SPIKE реализовать только:

```python
class TelnyxSmsSender(SmsSenderPort):
    provider_name = "telnyx"
    def send(self, *, to_e164: str, text: str) -> SmsSendResult: ...
```

Verify API не включать в MVP-контракт. При необходимости позже добавить отдельный порт:

```python
class PhoneVerifyProviderPort(Protocol):
    def start_verification(...): ...
    def check_verification(...): ...
```

## 2. Спецификация `send(to_e164, text)`

### 2.1 Endpoint

```text
POST https://api.telnyx.com/v2/messages
```

Base URL:

```text
https://api.telnyx.com
```

Path:

```text
/v2/messages
```

Method:

```text
POST
```

Telnyx request/response fundamentals document `POST /v2/messages` as the send-message operation.  
Source: https://developers.telnyx.com/development/api-fundamentals/request-response

### 2.2 Authentication

Telnyx uses API keys as the primary authentication method. Most Telnyx APIs, including Messaging API, use Bearer token authentication in the `Authorization` header.

```http
Authorization: Bearer <TELNYX_API_KEY>
Content-Type: application/json
Accept: application/json
```

Sources:
- https://developers.telnyx.com/development/api-fundamentals/authentication
- https://developers.telnyx.com/api-reference/messages/send-a-message

### 2.3 Required request fields for DOGEstonia

For our MVP, use SMS-only payload:

```json
{
  "from": "DOGEstonia",
  "to": "+372XXXXXXXX",
  "text": "Your DOGEstonia verification code is 123456",
  "messaging_profile_id": "00000000-0000-0000-0000-000000000000",
  "type": "SMS"
}
```

Field mapping:

| Telnyx field | Required by Telnyx | DOGEstonia source | Notes |
|---|---:|---|---|
| `to` | yes | `to_e164` | Receiving address. Telnyx requires `+E.164` formatted phone number or short code. For DOGEstonia, only E.164 phone numbers are allowed. |
| `text` | yes for SMS | `text` | Ready OTP text generated by DOGEstonia core. Telnyx only delivers it. |
| `from` | required when sending with phone number, short code, or alphanumeric sender ID | `TELNYX_FROM` | For Estonia, recommended MVP value: alphanumeric sender ID such as `DOGEstonia`, subject to account/profile setup. |
| `messaging_profile_id` | required when sending via number pool or with an alphanumeric sender ID | `TELNYX_MESSAGING_PROFILE_ID` | Required for alphanumeric sender path, which is recommended for EE. |
| `type` | optional enum | constant `SMS` | Telnyx supports `SMS` or `MMS`. Set explicitly to `SMS` to avoid ambiguity. |
| `encoding` | optional enum | `TELNYX_ENCODING` or omit | Default is `auto`; allowed values: `auto`, `gsm7`, `ucs2`. For OTP, `auto` is acceptable; `gsm7` can force failures if non-GSM chars are introduced. |
| `webhook_url` | optional | omit for MVP v1 or set later | Per-message webhook URL for delivery notifications. Not required for synchronous acceptance. |
| `use_profile_webhooks` | optional, default `true` | omit | Telnyx will use profile webhooks for delivery notifications if configured. |

Sources:
- https://developers.telnyx.com/api-reference/messages/send-a-message
- https://developers.telnyx.com/docs/messaging/messages/alphanumeric-sender-id

### 2.4 Recommended MVP request payload

Because Estonia supports maintained alphanumeric sender IDs with no registration required according to Telnyx Estonia SMS guidelines, and because Telnyx now requires a default alphanumeric sender ID on Messaging/Verify profiles for non-US destinations, the recommended MVP sender path is:

```json
{
  "from": "DOGEstonia",
  "to": "+372XXXXXXXX",
  "text": "Your DOGEstonia verification code is 123456",
  "messaging_profile_id": "${TELNYX_MESSAGING_PROFILE_ID}",
  "type": "SMS"
}
```

Sources:
- Estonia guidelines: https://support.telnyx.com/en/articles/6560919-estonia-sms-guidelines
- Messaging profile update: https://support.telnyx.com/en/articles/3562059-setting-up-a-messaging-profile
- Alphanumeric sender docs: https://developers.telnyx.com/docs/messaging/messages/alphanumeric-sender-id

### 2.5 cURL example

```bash
curl -X POST "https://api.telnyx.com/v2/messages" \
  -H "Authorization: Bearer ${TELNYX_API_KEY}" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{
    "from": "DOGEstonia",
    "to": "+37251234567",
    "text": "Your DOGEstonia verification code is 123456",
    "messaging_profile_id": "00000000-0000-0000-0000-000000000000",
    "type": "SMS"
  }'
```

### 2.6 Successful response

Telnyx `POST /v2/messages` returns HTTP `200` with a `data` object. The response includes:

- `data.id`: message UUID. This should become `SmsSendResult.provider_message_id`.
- `data.to[0].status`: e.g. `queued`. This means the message has been accepted/queued by Telnyx, not necessarily delivered to handset.
- `data.errors`: array, normally empty in successful example.
- `data.received_at`, `sent_at`, `completed_at`: status timestamps; `sent_at` and `completed_at` may be null at initial response.

Implementation rule:

```python
provider_message_id = response["data"].get("id")
accepted = response.status_code == 200 and response["data"]["to"][0]["status"] in {"queued", "sent"}
```

If status is `queued`, return `accepted=True`. Delivery confirmation is asynchronous and should not block `/auth/phone/request`.

Source: https://developers.telnyx.com/api-reference/messages/send-a-message

### 2.7 Delivery statuses and webhooks

Telnyx outbound statuses include:

| Status | Meaning | Final? |
|---|---|---:|
| `queued` | Message accepted and queued for sending | no |
| `sent` | Delivered to carrier gateway | no |
| `delivered` | Carrier confirmed delivery to handset | yes |
| `failed` | Delivery failed, see `errors` array | yes |
| `gw_timeout` | No response from gateway | yes |
| `dlr_timeout` | No delivery receipt from carrier | yes |

Telnyx recommends tracking delivery with webhooks rather than polling, using events such as `message.sent`, `message.delivered`, and `message.finalized`.

Source: https://developers.telnyx.com/docs/messaging/messages/message-detail-records

MVP decision: do not implement delivery webhook for PV-06 unless desired for observability. The OTP confirmation flow itself is the practical proof of delivery.

## 3. Telnyx → DOGEstonia `SmsErrorCode` mapping

### 3.1 Mapping table

| DOGEstonia `SmsErrorCode` | Telnyx HTTP status / code / condition | Source | Adapter behavior |
|---|---|---|---|
| `INVALID_PHONE` | HTTP 4xx with general API code `10002 Invalid phone number`; `10016 Phone number must be in +E.164 format`; messaging API request code `40310 Invalid 'to' address`; async delivery code `40012 Invalid destination number`; async `40001 Not routable`; async `40008 Undeliverable` when clearly destination-number related | API errors + Messaging errors | Raise immediately for synchronous request errors. For async delivery errors, store only if webhook implemented. |
| `COUNTRY_NOT_ALLOWED` | Messaging API request code `40309 Invalid destination region` = destination country not in profile whitelist; `40331 Missing whitelist` = no whitelisted destinations on profile | Messaging errors | Raise `COUNTRY_NOT_ALLOWED`; fix Telnyx Messaging Profile allowed destinations. |
| `RATE_LIMITED` | HTTP `429` with general API code `10011 Too many requests`; messaging code `40318 Queue full`; async/upstream code `40011 Rate limit exceeded (upstream)`; sender/account throughput limits | API rate limiting + Messaging rate limiting + Messaging errors | Raise `RATE_LIMITED`; use exponential backoff only for internal retry policy, but avoid duplicate OTP SMS unless idempotency strategy exists. |
| `PROVIDER_UNAVAILABLE` | HTTP `5xx` (`500`, `502`, `503`, `504`); network timeout; general code `10008 Request timeout`; async temporary delivery codes `40006 Recipient unavailable`, maybe `40008 Undeliverable` when treated as temporary | Request/response + API errors + Messaging errors | Raise `PROVIDER_UNAVAILABLE` for sync 5xx/network/timeout. Async errors require webhook handling. |
| `SEND_FAILED` | Messaging request/config errors not caused by user phone or country: `40305 Invalid from address`, `40306 Alpha sender not configured`, `40307 Alpha sender mismatch`, `40312 Profile disabled`, `40314 Messaging disabled`, `40315 Unhealthy sender`, `40320 Temporarily unusable sender`, `40321 No usable numbers in pool`, `40323 Activation failed`, `40325 Invalid alpha sender ID`, `40333 Spend limit reached`, `40100 Not messaging enabled`, `40009 Invalid message body`, `40302 Message too large`, `40316 No content`, `40322 Blocked content` | Messaging errors | Raise `SEND_FAILED`; log Telnyx `code/title/detail`; this is usually configuration/content/account issue, not retryable by user. |
| `UNKNOWN` | Any unexpected response shape, missing `data.id`, unclassified `errors[].code`, non-JSON response, undocumented code | Telnyx response/error shape docs | Raise `UNKNOWN`; include safe metadata in logs, never OTP text. |

### 3.2 Error body shape

Telnyx error responses use an `errors` array with objects containing fields such as:

```json
{
  "errors": [
    {
      "code": "10001",
      "title": "Invalid parameter",
      "detail": "The 'to' field is required",
      "source": {
        "pointer": "/data/attributes/to"
      }
    }
  ]
}
```

Sources:
- https://developers.telnyx.com/development/api-fundamentals/request-response
- https://developers.telnyx.com/development/api-fundamentals/api-errors

### 3.3 Notes on synchronous vs asynchronous errors

Telnyx distinguishes:

1. API request errors returned immediately.
2. Delivery errors after message acceptance, visible in message detail records and `message.finalized` webhooks.
3. Configuration errors.

For MVP, `TelnyxSmsSender.send(...)` can only map synchronous HTTP response errors. Async delivery failures cannot be returned synchronously from `/auth/phone/request` and require a webhook story if we want to record them.

Source: https://developers.telnyx.com/docs/messaging/messages/error-codes/index

- `TELNYX_API_KEY`: required for Bearer auth.
- `TELNYX_API_BASE_URL`: default `https://api.telnyx.com`; keep configurable for tests/mocks.

- `TELNYX_MESSAGING_PROFILE_ID`: required when using alphanumeric sender ID.
- `TELNYX_MESSAGE_TYPE`: set to `SMS` to avoid MMS ambiguity.
- `TELNYX_ENCODING`: Telnyx default is `auto`; keep configurable only if we later need forced `gsm7` or `ucs2`.

## 5. Answers to brief §7 questions

### Auth & basic

**1. Method of authentication.**  
Bearer API key in `Authorization: Bearer <token>`. API keys are managed in the Telnyx Mission Control Portal.  
Source: https://developers.telnyx.com/development/api-fundamentals/authentication

**2. Base URL / version / sandbox.**  
Base URL for Messaging API: `https://api.telnyx.com/v2/messages`. API version is v2. I found trial-account testing and on-net testing flows, but I did not find a documented Messaging API sandbox host or fake SMS test endpoint in the developer docs. Trial accounts can test messaging only to a verified number and have limits on delivery attempts.  
Sources:
- https://developers.telnyx.com/docs/messaging/messages/send-message
- https://developers.telnyx.com/docs/account-setup/using-trial-account

### Sending SMS: Path A

**3. Endpoint.**  
`POST https://api.telnyx.com/v2/messages`.  
Source: https://developers.telnyx.com/api-reference/messages/send-a-message

**4. Required/optional fields.**  
Required for DOGEstonia SMS: `to`, `text`, `from`, and for alphanumeric sender ID, `messaging_profile_id`. Optional useful fields: `type=SMS`, `encoding`, `webhook_url`, `webhook_failover_url`, `use_profile_webhooks`.  
Source: https://developers.telnyx.com/api-reference/messages/send-a-message

**5. Successful response.**  
HTTP `200` with `data.id`, `data.to[].status`, `data.errors`, and timestamps. Example status is `queued`; this is synchronous acceptance/queueing, not handset delivery.  
Source: https://developers.telnyx.com/api-reference/messages/send-a-message

**6. Error format.**  
General error response body: `errors[]` with `code`, `title`, `detail`, optional `source.pointer`. Messaging-specific errors are documented separately.  
Sources:
- https://developers.telnyx.com/development/api-fundamentals/request-response
- https://developers.telnyx.com/docs/messaging/messages/error-codes/index

**7. Idempotency.**  
❓ I did not find official Telnyx Messaging API documentation for an idempotency key on `POST /v2/messages`. Treat idempotency as not available until confirmed by Telnyx support or API reference.  
Architecture implication: no automatic HTTP retry after request body has been sent unless the failure occurred before receiving any HTTP response and product accepts possible duplicate SMS risk.

### Sender and countries

**8. Allowed sender types and Estonia.**  
Telnyx send-message endpoint supports phone number, alphanumeric sender ID, short code, or number pool. The `from` field can be E.164 phone number, alphanumeric sender ID, or short code. For Estonia, Telnyx Help Center says MCC `248`, dial code `372`, and alphanumeric sender IDs are supported/maintained with no registration required.  
Sources:
- https://developers.telnyx.com/api-reference/messages/send-a-message
- https://support.telnyx.com/en/articles/6560919-estonia-sms-guidelines

**9. Sender ID / A2P / brand-campaign registration for EE.**  
For Estonia, Telnyx Help Center says alphanumeric sender IDs are supported and maintained, no registration required. I found no EE-specific A2P/brand-campaign registration requirement in Telnyx docs. Note: Telnyx says some countries require sender ID pre-registration, but Estonia-specific page says no registration.  
Sources:
- https://support.telnyx.com/en/articles/6560919-estonia-sms-guidelines
- https://developers.telnyx.com/docs/messaging/messages/alphanumeric-sender-id

**10. Destination country restrictions / allowlist.**  
Telnyx Messaging Profiles can manage allowed international destinations. Telnyx Help Center says creating/editing Messaging or Verify Profiles requires configuring whitelisted destination countries for outbound termination. Messaging errors include `40309 Invalid destination region` and `40331 Missing whitelist`.  
Sources:
- https://support.telnyx.com/en/articles/3562059-setting-up-a-messaging-profile
- https://developers.telnyx.com/docs/messaging/messages/error-codes/index

### Delivery/statuses

**11. Synchronous acceptance and delivery receipts.**  
Synchronous `POST /v2/messages` response can return `to[].status = queued`, which means accepted and queued. Handset delivery is async; Telnyx recommends webhooks for `message.sent`, `message.delivered`, `message.finalized`.  
Source: https://developers.telnyx.com/docs/messaging/messages/message-detail-records

MVP: no delivery webhook required for phone verification, because actual user code entry proves practical delivery. Add webhook later for analytics/observability/fraud.

### Limits / format / text

**12. Rate limits.**  
Telnyx documents both API request rate limits and messaging throughput limits. API rate-limited responses use HTTP `429` and code `10011`. Default messaging throughput: account SMS 50 messages/second; long code 0.1 MPS per number; alphanumeric 0.1 MPS per sender ID; queue full returns `40318`. For MVP OTP traffic, alphanumeric 0.1 MPS means roughly one SMS every 10 seconds per sender ID, unless account-specific limits differ or Telnyx increases limits.  
Sources:
- https://developers.telnyx.com/development/api-fundamentals/reliability/rate-limiting
- https://developers.telnyx.com/docs/messaging/messages/rate-limiting

**13. Phone/text format, encoding, segmentation.**  
Telnyx requires E.164 format with `+`, country code and full number, no spaces/punctuation. For `POST /messages`, `text` is a non-empty string and required for SMS. Encoding default is `auto`; alternatives are `gsm7` and `ucs2`.  
Sources:
- https://developers.telnyx.com/docs/messaging/messages/send-message
- https://developers.telnyx.com/api-reference/messages/send-a-message

**14. Verify/OTP API.**  
Verify API exists. It can send a verification via `POST /v2/verifications/sms` with `phone_number` and `verify_profile_id`, and verify code via a verification action endpoint. This is managed verification, not compatible with current thin `SmsSenderPort` as the primary adapter.  
Sources:
- https://developers.telnyx.com/docs/identity/verify
- https://developers.telnyx.com/docs/identity/verify/quickstart

### Account/access for SPIKE

**15. What must be created.**

For live/SPIKE:

1. Telnyx account.
2. API key.
3. Messaging Profile.
4. Allowed destination country whitelist including Estonia / EE / +372.
5. Default alphanumeric sender ID on Messaging Profile for non-US destination sending.
6. `TELNYX_FROM` matching configured alphanumeric sender ID, e.g. `DOGEstonia`, or an alternative sender type.
7. Balance/payment method or trial account constraints handled.
8. For trial: verify a phone number and test to that verified number only; trial accounts have limits.

Sources:
- https://developers.telnyx.com/docs/messaging/messages/send-message
- https://developers.telnyx.com/docs/account-setup/using-trial-account
- https://support.telnyx.com/en/articles/3562059-setting-up-a-messaging-profile

## 6. Несостыковки и предлагаемая корректировка архитектуры

### 6.1 Managed Verify is not the only option

Status: ✅ no mismatch.

Telnyx supports normal Messaging API sending. No need to change the DOGEstonia thin provider contract.

### 6.2 Synchronous acceptance exists, but final delivery is webhook-based

Status: ⚠️ partial mismatch, expected and acceptable.

Telnyx synchronous response gives message ID and queued status. Final delivery or failure after queueing is asynchronous and should be consumed through delivery webhooks if needed.

Architecture correction:

- PV-06: treat HTTP 200 + `data.id` + `to[0].status in {'queued', 'sent'}` as `SmsSendResult(accepted=True)`.
- Do not promise final delivery in `/auth/phone/request`.
- Add optional post-MVP story: `PV-08 Telnyx delivery webhook ingestion`, storing status by `provider_message_id`.

### 6.3 Sender configuration for Estonia

Status: ⚠️ setup-sensitive.

Estonia supports alphanumeric sender IDs without registration according to Telnyx Help Center, but Telnyx also requires Messaging/Verify Profiles to configure whitelisted destination countries and, for non-US destinations, a default alphanumeric sender ID on the Messaging Profile.

Architecture correction:

- Require `TELNYX_MESSAGING_PROFILE_ID` for EE alphanumeric path.
- In SPIKE, explicitly configure allowed destination `Estonia` and default alpha sender.
- Add startup config validation: if `TELNYX_FROM` is not E.164 and looks alphanumeric, require `TELNYX_MESSAGING_PROFILE_ID`.

### 6.4 Country whitelist requirement

Status: ⚠️ mismatch with “just API key + from” minimal assumption.

Telnyx profile-level destination whitelist can block sends to Estonia if EE is not enabled, producing `40309` or `40331`.

Architecture correction:

- Keep DOGEstonia core allowlist (`PHONE_ALLOWED_COUNTRY_CODES=EE`) as business gate.
- Also require Telnyx Messaging Profile whitelist for EE as provider-side control.
- Map `40309` and `40331` to `COUNTRY_NOT_ALLOWED`.

### 6.5 Format is E.164

Status: ✅ no mismatch.

Telnyx requires E.164. This matches DOGEstonia `to_e164` contract.

### 6.6 Rate limits may be low for alphanumeric sender

Status: ⚠️ possible MVP constraint.

Telnyx default sender throughput for alphanumeric sender ID is documented as `0.1 MPS` per sender ID. This is enough for early MVP but can bottleneck bursts.

Architecture correction:

- Add DOGEstonia-side rate limit lower than Telnyx limit, e.g. one OTP send per phone/user/IP per 60 seconds.
- Queue or reject repeated requests in core before calling Telnyx.
- For growth, ask Telnyx to increase limits or switch sender strategy.

### 6.7 Sandbox/test mode

Status: ⚠️ unresolved.

I found trial/live testing docs but did not find a separate Messaging API sandbox base URL or fake SMS endpoint in official developer docs.

Architecture correction:

- Keep `TELNYX_API_BASE_URL` configurable for a local fake server in automated tests.
- For CI/unit tests, do not hit Telnyx; use fake `SmsSenderPort`.
- For SPIKE, use Telnyx trial/live testing to verified numbers.

### 6.8 Idempotency

Status: ⚠️ unresolved.

I did not find official documentation that `POST /v2/messages` supports idempotency keys.

Architecture correction:

- Do not blindly retry after ambiguous network failures.
- Store OTP request session before send with unique internal request ID.
- Allow manual retry from user after cooldown; old OTP should be invalidated or replaced according to DOGEstonia core policy.
- Add `provider_message_id` once returned.

## 9. Implementation sketch for `TelnyxSmsSender`

```python
class TelnyxSmsSender:
    provider_name = "telnyx"

    def __init__(self, runtime: SmsProviderRuntime):
        self.http = runtime.http_client
        self.settings = runtime.settings

    def send(self, *, to_e164: str, text: str) -> SmsSendResult:
        payload = {
            "from": self.settings.from_,
            "to": to_e164,
            "text": text,
            "type": "SMS",
        }
        if self.settings.messaging_profile_id:
            payload["messaging_profile_id"] = self.settings.messaging_profile_id
        if self.settings.encoding:
            payload["encoding"] = self.settings.encoding

        response = self.http.post(
            f"{self.settings.api_base_url.rstrip('/')}/v2/messages",
            headers={
                "Authorization": f"Bearer {self.settings.api_key}",
                "Content-Type": "application/json",
                "Accept": "application/json",
            },
            json=payload,
        )

        if response.status_code == 200:
            body = response.json()
            data = body.get("data") or {}
            message_id = data.get("id")
            to_entries = data.get("to") or []
            first_status = (to_entries[0].get("status") if to_entries else None)
            if message_id and first_status in {"queued", "sent"}:
                return SmsSendResult(provider_message_id=message_id, accepted=True)
            raise SmsSenderError("Unexpected Telnyx success response", code=SmsErrorCode.UNKNOWN)

        error_code = extract_telnyx_error_code(response)
        raise map_telnyx_error(response.status_code, error_code)
```
