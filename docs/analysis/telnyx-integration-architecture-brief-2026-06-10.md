# Telnyx ↔ DOGEstonia: архитектурный бриф для интеграции (вход для агента по докам Telnyx)

> **Кому и зачем.** Это **наш контракт-вход** для агента, который специализированно изучит developer-документацию Telnyx и выдаст **итоговый интеграционный документ**: либо «всё ложится на наш контракт — вот точные endpoints/поля/ошибки», либо «вот несостыковки» (тогда мы скорректируем архитектуру). Документ самодостаточен: здесь зафиксировано, **куда** Telnyx встраивается, **какой контракт** обязан выполнить адаптер, и **на какие вопросы** агент должен ответить из доков.
> **Что НЕ делать агенту.** Не подгонять факты под желаемое и не «угадывать» — если Telnyx работает иначе, чем ждёт наш контракт, это **несостыковка**, её надо явно выписать (см. §6), а не замаскировать.
> **Метод:** [`analysis.mdc`](../../../.cursor/rules/analysis.mdc) — только проверяемые факты из официальной документации Telnyx, со ссылками.
> **База:** архитектура [`phone-verification-architecture-2026-06-10.md`](phone-verification-architecture-2026-06-10.md); паттерны зеркалятся с готовой eID-платформы (код, 🟢 Done).

## 1. Контекст в одном абзаце

Мы делаем **разовую верификацию телефона** (доказать, что за аккаунтом реальный человек): пользователь вводит номер → мы шлём 6-значный OTP по SMS → он вводит код обратно → ставим флаг `phone_verified`. SMS-провайдеры **сменные и подключаемые** (активный выбирается в `.env`), коды разрешённых стран — в `.env`. **Telnyx — первый боевой провайдер.** Его задача в нашей модели — **доставить SMS** (генерацию и сверку кода держим у себя). Агент должен подтвердить, что Telnyx это умеет так, как нам нужно, либо указать расхождения.

## 2. Куда именно встраивается Telnyx (наша архитектура)

```
  POST /auth/phone/request ─┐
                            ▼
        ┌─────────────────────────────────────┐        ┌───────────────────────────┐
        │ Ядро (provider-agnostic, наше)       │        │ .env                       │
        │ • нормализация E.164                 │        │ SMS_PROVIDER=telnyx        │
        │ • проверка кода страны ∈ allowlist   │◀───────│ PHONE_ALLOWED_COUNTRY_CODES│
        │ • генерация OTP, hash, TTL, attempts  │        │ TELNYX_* (creds/sender)    │
        │ • запись сессии, аудит               │        └───────────────────────────┘
        └───────────────┬─────────────────────┘
                        │ send(phone_e164, text)              ◀── ЕДИНСТВЕННАЯ точка стыка с Telnyx
                        ▼
        ┌─────────────────────────────────────┐        ┌───────────────────────────┐
        │ SmsSenderPort (контракт адаптера)    │        │ SmsProviderRuntime (DI)    │
        │  TelnyxSmsSender.send(...)           │◀───────│ http_client (httpx, sync) │
        │  → SmsSendResult | raise             │        │ settings (TelnyxSettings) │
        │    SmsSenderError(SmsErrorCode)      │        └───────────────────────────┘
        └───────────────┬─────────────────────┘
                        │ HTTPS
                        ▼
                 ░░ Telnyx API ░░   ◀── агент описывает ЭТОТ слой по докам
```

**Важно про границу ответственности (наша модель «тонкого провайдера»):**
- **Наше ядро** владеет: генерацией OTP, его хранением (хэш), сверкой введённого кода, сроком жизни, счётчиком попыток, флагом профиля. Это **не** отдаём провайдеру.
- **Telnyx (адаптер)** владеет: **только доставкой SMS** с нашим текстом на номер.

> Эта граница — следствие требования «провайдеры сменные»: так подключается **любой** SMS-провайдер, а не только умеющий managed-OTP. См. форк §5 — если у Telnyx доставка устроена иначе, это влияет на контракт.

**Что из этого уже код, а что план:**
- ✅ **Реальный код (образец для зеркала):** провайдер-платформа eID — порт [`base.py`](../../src/core/providers/base.py), дескриптор [`descriptor.py`](../../src/core/providers/descriptor.py), конфиг-спека [`config_spec.py`](../../src/core/providers/config_spec.py), DI-рантайм [`runtime.py`](../../src/core/providers/runtime.py), сборка реестра [`registry_builder.py`](../../src/core/providers/registry_builder.py), HTTP-клиент в рантайме [`runtime_factory.py`](../../src/core/providers/runtime_factory.py); HMAC [`hashing.py`](../../src/core/security/hashing.py); флаг профиля `eid_verified`/`verified_person_hash` [`models.py:23-40`](../../src/core/domain/models.py).
- 🟦 **План (ещё не код):** весь `phone`-слой (`SmsSenderPort`, `TelnyxSmsSender`, OTP-движок, `/auth/phone/*`). Описан как контракт ниже — агент проверяет Telnyx **против него**.

## 3. Контракт, который адаптер Telnyx ОБЯЗАН выполнить

### 3.1. Порт (поверхность вызова)
```python
class SmsSenderPort(Protocol):
    @property
    def provider_name(self) -> str: ...          # "telnyx"
    def send(self, *, to_e164: str, text: str) -> SmsSendResult: ...
    # при сбое — raise SmsSenderError(message, code=SmsErrorCode.X)
```
- Вход: `to_e164` (номер в формате E.164, напр. `+372…`), `text` (готовая строка с OTP — формирует ядро).
- Выход (успех): `SmsSendResult` — минимум `provider_message_id: str | None`, `accepted: bool` (Telnyx принял к отправке).
- Синхронность: вызов **синхронный** (наш рантайм даёт `httpx.Client`, не async).

### 3.2. Канон ошибок (vendor → наш `SmsErrorCode`)
Адаптер обязан маппить ошибки Telnyx в **наш** канон (ядро/SPA знают только его). Таблицу заполняет агент по докам Telnyx:

| Наш `SmsErrorCode` | Когда | Какой ответ/код Telnyx сюда мапится (заполнить агенту) |
|--------------------|-------|--------------------------------------------------------|
| `INVALID_PHONE` | номер некорректен/недоставляем | ❓ |
| `COUNTRY_NOT_ALLOWED` | страна назначения запрещена на стороне Telnyx | ❓ (если Telnyx сам режет; у нас есть и свой allowlist) |
| `RATE_LIMITED` | троттлинг провайдера | ❓ (HTTP 429 / код) |
| `PROVIDER_UNAVAILABLE` | 5xx / сеть / таймаут | ❓ |
| `SEND_FAILED` | прочий отказ отправки | ❓ |
| `UNKNOWN` | неклассифицированное | fallback |

*(Канон `SmsErrorCode` зеркалит `EidErrorCode` из [`base.py`](../../src/core/providers/base.py); коды сверки OTP — `CODE_MISMATCH`/`CODE_EXPIRED`/`TOO_MANY_ATTEMPTS` — это ядро, не Telnyx.)*

### 3.3. Конфиг (что адаптер ждёт из `.env` через config_spec)
Предполагаемый набор (агент уточняет/корректирует по докам):
```
TELNYX_API_KEY            (required) — Bearer-ключ
TELNYX_FROM               — отправитель: номер E.164 ИЛИ messaging profile id ИЛИ alphanumeric sender (❓ что применимо для EE)
TELNYX_MESSAGING_PROFILE_ID — если отправка идёт через профиль (❓)
TELNYX_API_BASE_URL       (optional) — на случай sandbox/иного хоста
```
Валидация обязательных полей — делегированная, по образцу [`config_spec.py`](../../src/core/providers/config_spec.py) (как у eID `AUTHENTIGATE_*`).

### 3.4. DI, который адаптер получит
`SmsProviderRuntime` (зеркало [`runtime.py`](../../src/core/providers/runtime.py)): `http_client: httpx.Client` (sync, общий, с таймаутом), `settings: TelnyxSettings`, `config`. Адаптер **не** создаёт свой HTTP-клиент.

## 4. Поток, в котором живёт `send` (чтобы агент понимал требования к доставке)

```
/auth/phone/request → [ядро: страна ок? → OTP → сессия started, TTL] → TelnyxSmsSender.send(to, text)
        success(accepted)  → ответ SPA { sent, expires_at }
        raise SmsErrorCode → ответ SPA { error, code }
/auth/phone/confirm → [ядро сверяет код, ставит phone_verified] — Telnyx тут НЕ участвует
```
Из этого — наши требования к доставке (их агент проверяет, см. §5–§6):
- Нам нужно **синхронно узнать**, принял ли Telnyx сообщение к отправке (для немедленного ответа `request`). Финальный delivery-receipt (доставлено/не доставлено абоненту) для MVP **не обязателен** — мы и так требуем ввод кода. Но если Telnyx **не** подтверждает приём синхронно (только webhook) — это влияет на обработку ошибок (см. §6).

## 5. Главный архитектурный форк (агент должен его разрешить по докам)

Telnyx, насколько известно, предлагает разные пути отправки/верификации. **Агент должен определить, что реально доступно, и какой путь рекомендуется**:

- **Путь A — Messaging API (наш базовый выбор):** мы шлём свой текст с OTP, Telnyx доставляет SMS. Идеально ложится на «тонкий» `SmsSenderPort` и сохраняет сменность провайдеров. ➡️ если доступно — описать endpoint отправки, auth, поля, ответ.
- **Путь B — Verify / OTP-API (managed):** Telnyx сам генерирует, шлёт и проверяет код. Это **«толстый» провайдер** — ломает нашу границу §2 (OTP уезжает на сторону Telnyx) и наш `SmsSenderPort`. ➡️ если по какой-то причине это единственный/настоятельно рекомендуемый путь — **это несостыковка** (§6), тогда мы пересматриваем порт на `PhoneVerifyProviderPort` (request/check) и ужимаем OTP-движок ядра.

**Что нужно от агента по форку:** какой путь поддерживается, ограничения каждого, и обоснованная рекомендация под наше требование «много сменных провайдеров». По умолчанию целимся в **A**.

## 6. Триггеры несостыковки (когда фиксировать проблему, а не подгонять)

Явно выписать как ⚠️, если по докам Telnyx обнаружится любое из:
1. **Только managed-Verify (нет «просто отправить SMS»)** → порт нужно менять (см. §5-B).
2. **Нет синхронного подтверждения приёма** (успех/ошибка только через webhook) → наш `request` не сможет сразу вернуть `SEND_FAILED`; решаем: считать 2xx достаточным и/или добавить webhook-обработчик (новая стори).
3. **Отправитель (`from`) для EE/Эстонии ограничен** (напр. alphanumeric sender запрещён, нужен купленный номер/short code, или нужна предрегистрация sender ID) → влияет на конфиг и на SPIKE (закупка номера).
4. **Жёсткие country-ограничения/требования регистрации трафика** (напр. A2P-регистрация, запрет на EE без верификации) → влияет на сроки и на наш allowlist.
5. **Формат номера не E.164 / иные требования** к `to`/`from` → влияет на нормализацию ядра.
6. **Rate limits ниже наших ожиданий** (троттлинг на отправку) → влияет на наш rate-limit на `request`.
7. **Нет sandbox/тестового режима** для offline/CI → влияет на тест-план (live-only).
8. **Идемпотентность отправки** недоступна → возможны дубли SMS при ретраях; зафиксировать.

Любой триггер → раздел «Несостыковки и предлагаемая корректировка архитектуры» в итоговом документе агента.

## 7. Вопросы к документации Telnyx (агент отвечает фактами + ссылками)

**Auth & базовое**
1. Метод аутентификации (Bearer API key? V2 key?), где берётся, как передаётся.
2. Base URL(ы), версия API, sandbox/test-режим (есть ли).

**Отправка SMS (Путь A)**
3. Точный endpoint отправки сообщения (метод, путь).
4. Обязательные/опциональные поля запроса (`to`, `from`/`messaging_profile_id`, `text`, и пр.).
5. Формат успешного ответа: есть ли `message id`, статус «принято к отправке» (синхронно?).
6. Формат ошибок: HTTP-коды + тело (`errors[].code/title/detail`?) — для таблицы §3.2.
7. Идемпотентность (idempotency key) — поддерживается?

**Отправитель и страны**
8. Какие типы `from` допустимы (E.164-номер / messaging profile / alphanumeric sender) и что применимо для доставки в **Эстонию (EE, +372)**.
9. Нужна ли предварительная регистрация sender ID / A2P / brand-campaign для EE и сколько занимает.
10. Ограничения по странам назначения, как включаются.

**Доставка/статусы**
11. Синхронно ли известен исход приёма; как устроены delivery receipts (webhook?) — нужно ли нам их слушать для MVP.

**Лимиты/прочее**
12. Rate limits на отправку.
13. Требования к формату номера (E.164?), к длине/кодировке текста (GSM-7/Unicode, сегментация).
14. Verify/OTP-API (Путь B): существует ли, его endpoints (`verify`/`verifications`), ограничения — для оценки форка §5.

**Аккаунт/доступ (для SPIKE)**
15. Что нужно завести для боевой/тестовой отправки: ключ, номер/профиль, пополнение баланса, верификация аккаунта.

## 8. Что должен содержать итоговый документ агента

1. **Вердикт по форку §5** (Путь A или B) + обоснование под «сменные провайдеры».
2. **Заполненную таблицу ошибок §3.2** (Telnyx → `SmsErrorCode`).
3. **Точную спецификацию `send`**: endpoint, auth, поля запроса/ответа, пример (curl/JSON) — чтобы реализовать `TelnyxSmsSender` без догадок.
4. **Финальный список `TELNYX_*` env** (скорректированный под реальность) для config_spec и `.env.example`.
5. **Раздел «Несостыковки и корректировки архитектуры»** (если сработали триггеры §6) — конкретно, с предлагаемым решением.
6. **Чек-лист для SPIKE** (аккаунт/номер/страны/тест-режим) для человека.
7. Все утверждения — со **ссылками на конкретные страницы доков Telnyx**.
