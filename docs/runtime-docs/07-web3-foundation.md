# 07. Web3-заготовка (на будущее)

## О чём этот документ и честное предупреждение

Идея на перспективу: дать пользователю привязать криптокошелёк и подписывать им свои действия (доказательство авторства, портативная гражданская идентичность). **Сейчас этого нет.** В коде есть только **зарезервированные поля в таблице профиля** — места, куда когда-нибудь лягут данные кошелька. Никакой логики (подписи, работы с блокчейном) нет. Этот документ честно фиксирует, что именно «застолблено», чтобы потом было легче встроить, и чтобы никто не принял заготовку за готовую фичу.

**Общий статус: ⚪ только заготовка.**

Источник: [`profiles` миграция](../../supabase/migrations/20260525000001_create_profiles.sql), [`domain/models.py`](../../src/core/domain/models.py), [`infrastructure/db_supabase.py`](../../src/core/infrastructure/db_supabase.py).

## Что реально застолблено

**Колонки в `profiles`** ([миграция:22-27](../../supabase/migrations/20260525000001_create_profiles.sql), секция `-- Wallet placeholder (Post-MVP)`):
- `wallet_address` (уникальный) — адрес кошелька;
- `wallet_linked_at` — когда привязан;
- `wallet_signature_verified_at` — когда проверена подпись;
- `wallet_signature_scheme` — схема подписи;
- `wallet_chain_id` — какая сеть.

Те же пять полей есть в модели `ProfileRecord` ([`models.py:34-38`](../../src/core/domain/models.py)), все по умолчанию пустые, и они проходят через весь маппинг чтения/записи в Supabase ([`db_supabase.py:103-107,125-131`](../../src/core/infrastructure/db_supabase.py)). То есть если значения кто-то проставит — они сохранятся и прочитаются. Но **никакой код их не заполняет**: при создании профиля все `wallet_*` ставятся в `None` ([`repositories.py:114-118`](../../src/core/infrastructure/repositories.py)).

## Чего нет (проверено по коду)

- ни библиотек web3/ethers, ни SIWE («вход подписью кошелька»);
- ни проверки подписи, ни обращений к блокчейн-сети/RPC, ни логики по `chain_id`;
- ни эндпоинтов привязки кошелька.
- Единственное «живое» правило — `wallet_address UNIQUE` на уровне БД (один адрес — один профиль).

## Зачем это сейчас держать

Это «крючки» в модели данных. Когда дойдут руки до web3-слоя, не понадобится миграция профиля под базовые поля — место под адрес, время привязки, факт и схему проверки подписи и сеть уже зарезервировано и протянуто через всю цепочку (БД → модель → Supabase-маппинг). Останется добавить собственно поведение: проверку подписи, эндпоинт привязки и заполнение этих полей.

> ⚠️ Поскольку поля есть, а кода нет — это «заготовка-плейсхолдер». Чтобы документация не создавала иллюзию готового web3, в [gap §10 (P1)](../analysis/gap-analysis-full-2026-06-04.md) эта заготовка вынесена отдельной строкой на решение «оставить/убрать».
